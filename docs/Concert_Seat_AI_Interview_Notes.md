# SeatView 项目面试讲解材料

> 个人项目，使用 AI 辅助开发（Vibe Coding），并基于当前代码整理产品设计与技术复盘。以下为参考口述，请按本人实际参与范围调整。时长为练习目标，不是已测量的口述结果。没有用户调研、经营指标、模型准确率或成本结果；Mock 不能称为真实大模型效果。

## 1. 1 分钟项目介绍

我做了一个个人项目 SeatView，是演唱会场馆座位视角查询与 AI 辅助选区的 Web MVP。它基于一个假设：购票前，用户很难仅凭座位图判断距离、角度、遮挡和拍摄体验。

我把范围收敛在一个完整南京场馆 Demo 和两条用户链路。用户可以搜索场馆、看座位图和结构化视角，再输入需求获得基于现有座区的推荐；运营可以粘贴观演描述，让模型生成字段初稿，人工修改确认后发布。


## 2. 3 分钟项目详细介绍

### 2.1 问题与范围

这个项目从演唱会购票前的信息判断出发。我的设计假设是：官方座位图能展示区的位置，但用户还需要知道现场角度、遮挡和拍摄条件；不同观演描述没有统一口径，比较起来比较费力。这个假设尚没有正式访谈支持，所以我先做可以验证的个人 MVP，而没有把它包装成已经找到市场需求的产品。

我保留现有搜索、场馆详情、图片、视角和后台功能，重点补齐南京一个完整 Demo，而不是增加很多只有名字的场馆。南京有五个示例座区，图和评价均提示演示性质，原有资料也保留。

### 2.2 两条业务链路

普通用户搜索场馆后，可以看地图、切换座区或筛选视角。AI 助手接受“正面看舞台”或“想拍直拍、无遮挡”等需求。后端读取当前场馆已发布记录，每区保留第一条；模型先输出偏好，本地规则排序出最多十二个候选，再让模型选择首选和最多两个备选。返回结果须通过 ID、数量、重复和评分校验，最终理由由已有字段拼装。

运营在后台输入描述，模型提取场馆、座区、距离、角度、遮挡、拍摄友好度、标签和总结。初稿不会自动保存，运营需要确认已有场馆并修改字段、补充来源，再保存成已发布视角。这样把自然语言整理和最终内容责任分开。

### 2.3 工程措施与真实边界

模型请求封装在 services，Prompt 集中维护，Key 只从后端环境变量读取。真实请求失败会明确显示降级原因；没有 Key 也可使用本地规则 Demo。此前实际接入中遇到后端网络超时和模型格式参数兼容问题，代码增加了显式代理、模型分支处理和严格 JSON 校验；已有验收报告记录真实推荐成功。本次回归测试也覆盖 Mock、保存、权限和非法推荐拦截，但不代表模型质量已经量化。


### 2.4 下一步验证

下一阶段我会先完善少量真实场馆信息，建立字段规范、来源核验和冲突评价处理，再用标注集评估抽取忠实度、推荐合法性和偏好匹配。并优先修复有候选却不适合时的拒答逻辑，补充调用时延与 Token 统计，而不是直接扩展复杂 Agent 或票务支付。

## 3. 为什么选择这个产品方向

参考回答：这个方向适合把“信息查找—比较—决策”和“内容录入—整理—发布”放在同一个小型产品里。用户侧能观察推荐解释是否支持取舍，运营侧能观察 AI 是否减少重复整理。我先把这些作为待验证的假设，选择一个完整场馆 Demo 来降低实现范围。现阶段的优势是问题具体、链路可演示；不是已经验证市场规模或用户增长。

追问“你做过用户调研吗？”时，应回答目前没有正式访谈或运营样本；下一步会让目标用户完成具体选区任务，观察他们需要哪些证据、是否信任推荐，再修正设计。

## 4. 为什么引入大模型

参考回答：模型主要处理自然语言理解，分别把观演描述变成字段、把购票需求变成偏好。场馆搜索、发布态过滤、数据关联和 ID 校验仍交给确定性代码。使用 API 是因为 MVP 没有训练集和训练需求，先验证应用是否有价值更合适。我没有做正式多模型质量/成本对比，也没有训练推荐模型。

如果只问“所有功能都需要 AI 吗？”：搜索不需要，当前就是本地匹配。简单偏好也可用规则，项目保留规则作为演示和降级；真实模型是否明显改善复杂表达，需要用同一评估集对比，不能仅凭体验下结论。

## 5. AI 智能录入解决了什么问题

参考回答：它解决的是运营把长文本拆成多个字段的初次整理问题。模型生成的是可修改初稿，未知字段应为空。运营必须确认场馆、座区、总结和来源才能发布，解析本身不写库。这条链路可用来验证整理耗时与人工修改率，但当前没有实际节省时间的数据。

追问“置信度 90% 是否意味着准确率？”：不是。当前 confidence 是模型自报，Mock 固定 0.65，未经校准；界面仅作参考，不能把它当成真实准确率或自动发布阈值。

## 7. API 调用和 AI 能力封装怎么做

参考回答：浏览器只访问同源 `/api/ai/extract`、`/api/ai/recommend` 和人工保存接口。Node 从环境读取提供商、模型、Key 和代理配置，调用兼容 Chat Completions。services/aiService.js 管请求、解析、校验和降级，prompts.js 管三个模板，aiConfig.js 管配置，proxyFetch.js 管可选代理。AI 不直接写库，保存由带后台权限的接口执行。

每次上游请求超时三十秒，正常推荐有两次串行调用。通用错误不会自动无限重试；只有结构化格式参数被明确拒绝时兼容重试一次。用户可再次点击发起请求。代码不把 Key 放到前端，也不会把原始上游错误正文展示给用户。

## 8. 当前系统是否真正属于 Agent

参考回答：当前整体是 AI Workflow，抽取是单次 LLM 调用，推荐是固定两步模型调用和代码校验。没有 tools 定义、模型选择工具、工具结果回传、决策循环或自主规划；Loading 和登录会话也不是 Agent 状态。

后续如果出现多步查证需求，可以设计少量只读工具，例如列座区、取证据、比较区域，让模型选择调用并接收结果，同时限制场馆范围、步数和时间。但这些尚未实现。当前固定流程更容易演示和验证，不需要为了名称升级复杂度。

## 9. 如何减少模型幻觉

参考回答：我分输入、输出和发布三个层次处理。输入只提供当前场馆已发布候选，Prompt 明确不编造；输出用候选 ID 白名单和数量/评分校验，理由由原字段生成，避免模型随意写价格；发布则要求运营人工确认。任何模型或格式失败明确降级，不能伪装成模型成功。

这些措施不能证明原评价是真实的，也不能保证合法 ID 满足用户需求。目前缺失语义质量评测、来源核验和可靠拒答。特别是 Prompt 允许空首选但代码要求非空，需要在后续修正。

## 10. 如何设计 AI 效果评估

参考回答：首先把代码约束测试与模型效果评估分开。已有测试验证路由、权限、Mock、保存、格式兼容和越界 ID 拦截；真实模型语义评估还未系统开展。


## 11. 项目最大的技术与产品难点


实际接入时，浏览器能打开网页但 Node 请求仍可能超时，需要显式后端代理；模型对 response_format 和输出长度的兼容也需要处理。对应修复有代码与已有报告依据，但我不会把它写成系统已稳定支撑生产流量。另一个重要发现是“JSON 合法”与“业务合理”不同，需要额外评估拒答和偏好匹配。

## 12. 如果继续迭代，下一步做什么

参考回答：我会先处理三个基础问题：第一，完善少量真实资料，记录来源、演出布局和核验状态；第二，允许不推荐，聚合同区冲突评价并给出明确不足；第三，补充人工初稿/最终值、调用模式、时延和 Token 的脱敏统计，建立标注集。

同时公开接口应只返回已发布数据，写入要避免并发覆盖，推荐接口需要调用保护。完成这些验证后，再决定是否需要工具调用助手。实时票价、支付和大规模采集不是当前优先级。

## 13. 简历项目经历参考：个人项目，按真实参与范围选用

项目名建议：**SeatView 演唱会座区查询与 AI 辅助决策平台｜个人项目（AI 辅助开发）**。

- 围绕购票前座区体验判断的需求假设，设计查询与运营双角色流程，将 MVP 收敛为一个完整场馆 Demo、结构化视角展示、AI 智能录入和座区推荐。
- 设计“自然语言抽取—可编辑预览—人工确认—发布”的运营闭环，定义距离、角度、遮挡和拍摄等字段，兼容原有视角结构并维护集中 Prompt。
- 通过 AI 辅助开发接入 OpenRouter 兼容 API，完成服务端环境配置、模型能力封装、JSON/候选校验及 Mock/fallback 提示，采用限定候选的两阶段推荐 Workflow。

不写虚构的“服务数千用户”“准确率提升”“降低成本”“推荐转化率增长”，不将个人项目写成企业实习。真实在线推荐可结合已有验收截图演示；真实抽取未重新在线验证时，应现场检查模式或使用明确标识的 Mock。

## 14. 现场展示与证据准备

1. 启动同一 Node 服务，确认实际端口。`npm start` 同时提供前后端，默认 5178；原浏览器演示曾使用 5180，不保证当前该进程与配置一致。
2. 首页搜“南京奥体中心”，进入详情，主动说明五个座区图和评价是示例，展示结构化字段与来源。
3. 输入拍摄或正面需求，展示模式、推荐依据和不足；如果 fallback 如实解释网络/格式降级，不将规则结果当真实模型输出。
4. 后台用本人配置密码登录，解析描述，修改字段后确认保存。这个演示会写正式数据，建议提前备份或在临时 DATA_DIR 中演示；不要公开凭据。
5. 用 `services/prompts.js`、`services/aiService.js` 和测试文件解释边界，再讲未完成事项。
